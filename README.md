# first-principles-architecture

> 先重建理想架构，再回头给现有代码分类--保留、重塑、替换、删除。别让打补丁打出来的历史代码决定系统的未来。

## 一句话总结

这是一个高质量的资深架构师型 Skill，适合在 CodeX 和 Claude Code 中用于大型重构、架构评审和老系统治理；它不会让 AI 更会写普通代码，但会显著降低 AI 把系统越改越乱的概率。

**作者画像**：有大型生产系统维护经验、熟悉 AI 编程代理、偏架构和技术决策角色的资深工程师或技术负责人。

## 这是什么

`first-principles-architecture` 是一个 Claude Code skill，把「第一性原理」当作**思维镜头**（不是强制仪式、不是报告模板、也不是固定工作流），用在技术计划、系统设计、重构提案、代码库问题和重大变更上。你显式调用它，它给你一个**架构判断**--不是一上来就改代码，不是默认甩出一份格式化报告。

大多数架构讨论从「现有代码长什么样」出发再讨论怎么改，而现有代码本身往往是打补丁打出来的。这个 skill 反过来：先想清楚系统本来应该是什么样，再回头给现有代码分类--**保留、重塑、替换、删除**。把现有代码当证据，不当需求。一句话：**让项目看上去像是一次性写出来的**

它是一个**透镜，不是重写令**：用第一性原理思考，不等于必须推倒重来。它不会让 AI 更会写普通代码，但会显著降低 AI 把系统越改越乱的概率。

## 什么时候用

- 要做一个重构方案，但拿不准改动边界划在哪、改到什么强度
- 一个系统越改越乱，想重新想清楚它「应该长什么样」
- 评审一份还没执行的 MD 计划，判断它是在修补旧结构还是建立正确结构
- 决定要不要重写一个子系统--这个 skill 会逼你先证明重写比改造划算
- 新功能要落地，想看清它该落在项目的哪个核心位置、暴露了哪些旧结构问题

## 什么时候不用

- 只想修个 bug、加个小功能--不需要架构推理，直接干
- 想要自动改代码--这个 skill **只给判断，不动手**（除非你明确要求实施）
- 纯探索性聊天、不想被方法论约束

## 怎么用

**仅主动触发**--模型不会从话题相似度自动激活，只在你显式调用时启动，不占用对话开始时的上下文。被调用后在当前计划 / 功能 / 重构任务中持续生效；换话题、方案定稿，或说「停止审视」时退出。

```
/first-principles-architecture
```

或带上要分析的对象：

```
$first-principles-architecture 看看 src/auth 这块该怎么重构
```

调用后先**自动判断在审视什么**（未执行的 MD 计划 / 新功能落点 / 整个项目 / 正在改的代码），上下文能判断的不反问。然后按以下几节推进：

1. **确立目标（Establish the target）** - 从系统必须产出的结果出发，找出最小必要的领域概念、不变量、职责、状态归属、外部接口。暂时忽略现有文件名和模块边界，把业务规则、数据兼容、运维约束当真实约束。
2. **对比目标与历史（Compare target and history）** - 目标模型成形后再看现有代码，分四类：保留 / 重塑 / 替换 / 删除。不奖励为复用而复用。
3. **选择改变策略（Choose the change strategy）** - 先和用户对齐改动强度：A 保守 / B 温和（默认）/ C 破坏性创造（C 档默认偏向删除旧东西，但仍避免无脑重写）。再从证据选手段：局部重构 / 增量迁移 / 有界替换 / 整体重写。优先选「让架构概念完整」的最小改动，而不是「留下矛盾模型」的最小 diff。
4. **保护概念完整性（Protect conceptual integrity）** - 一套领域语言、每个可变状态有唯一真源、每个用户动作有唯一执行路径、少而精的公开接口、过渡代码必须有明确 cutover 条件。
5. **沟通推理（Communicate the reasoning）** - 先讲根因再讲模块；区分观察与假设；**提问可以一次问多个、把相关的合并成一轮问清（最多两轮），不要一次只抛一个**；能自己查代码 / 测试 / 提交历史的就别问用户，只问用户独有的产品意图和历史原因，每个问题附建议答案；用大白话讲，用了术语马上补人话；不默认生成报告，把思考融入讨论。
6. **避免假第一性原理（Avoid false first principles）** - 不把「第一性原理」当装饰推销既定方案；旧代码不一定错，新设计不一定对；不为视觉整洁把复杂度挪到别处、不丢掉已验证的领域知识。

## 核心原则

- **目标先于现状**：先重建理想模型，再看现有代码--现有代码是证据，不是需求
- **判断重于执行**：只给架构判断，不擅自变成实施任务（除非用户明确要求）
- **强度对齐**：改动强度（保守 / 温和 / 破坏性）由用户定，破坏性档默认偏向删除但需证据和迁移计划
- **提问要合并**：相关问题一次问清、最多两轮，不要一次只问一个；能自查的不问用户
- **不移动复杂度**：不为视觉整洁把复杂度搬到别处，不留下永久兼容层和没有删除条件的过渡代码
- **警惕假第一性原理**：旧代码不一定错，新设计不一定对；把测试、数据格式、运维、失败处理、用户预期里编码的行为都算进去
