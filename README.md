# first-principles-architecture

> 先重建理想架构，再回头给现有代码分类——保留、重塑、替换、删除。别让打补丁打出来的历史代码决定系统的未来。

`first-principles-architecture` 是一个 Claude Code skill，把「第一性原理」当作**思考透镜**，用在技术计划、系统设计、重构提案、代码库问题和重大变更上。你显式调用它，它给你一个**架构判断**——不是一上来就改代码。

## 这是什么

大多数架构讨论从「现有代码长什么样」出发，再讨论怎么改。问题是现有代码本身就是打补丁打出来的，带着历史的妥协；从它出发往前推，往往只是把混乱换个地方。

这个 skill 反过来：先暂时忽略现有文件名、类、兼容层和历史模块边界，从「系统到底要产出什么」倒推出一套理想的目标模型——哪些概念必须存在、谁拥有什么状态、复杂度该放在哪。再回头把现有代码分成四类：**保留**（preserve）、**重塑**（reshape）、**替换**（replace）、**删除**（delete）。改的方向从「理想」出发，不从「现状」出发。

它是一个**透镜，不是强制仪式**：用第一性原理思考，不等于必须重写。很多时候结论是局部重构就够。

## 什么时候用

- 要做一个重构方案，但拿不准改动边界划在哪
- 一个系统越改越乱，想重新想清楚它「应该长什么样」
- 评审别人的架构计划，想判断它是不是真的概念自洽
- 决定要不要重写一个子系统——这个 skill 会逼你先证明重写比改造划算
- 新系统设计前，先把领域概念、状态归属、执行路径想清楚再下笔

## 什么时候不用

- 只想修个 bug、加个小功能——不需要架构推理，直接干
- 想要自动改代码——这个 skill **只给判断，不动手**（除非你明确要求实施）
- 纯探索性聊天、不想被方法论约束

## 怎么用

**仅主动触发**——模型不会从话题相似度自动激活，只在你显式调用时启动，不占用对话开始时的上下文。

```
/first-principles-architecture
```

或带上要分析的对象：

```
$first-principles-architecture 看看 src/auth 这块该怎么重构
```

skill 会按 6 个阶段推理：

1. **确立目标** — 系统必须产出什么？最小必要概念、不变量、职责、状态归属、外部接口。暂时忽略现有代码边界，把业务规则、数据兼容、运维约束当真实约束。
2. **对比目标与历史** — 等目标模型成形后再看现有代码，分四类：保留 / 重塑 / 替换 / 删除。不奖励为复用而复用。
3. **选择改变策略** — 从证据选：局部重构 / 增量迁移 / 有界替换 / 整体重写。优先选「让架构概念完整」的最小改动，而不是「留下矛盾模型」的最小 diff。
4. **保护概念完整性** — 一套领域语言、每个可变状态有唯一真源、每个用户动作有唯一执行路径、少而精的公开接口、过渡代码必须有明确 cutover 条件。
5. **沟通推理** — 先讲根因再讲模块；区分观察与假设；用你的语言和你的水平解释，必要时大白话 + 精确术语并用。
6. **避免假第一性原理** — 不把「第一性原理」当装饰来推销既定方案；旧代码不一定错，新设计不一定对；不为视觉整洁把复杂度挪到别处、不丢掉已验证的领域知识。

## 核心原则

- **目标先于现状**：先重建理想模型，再看现有代码——现有代码是证据，不是需求
- **最小且完整**：选能让架构概念完整的最小改动，不选留下矛盾模型或永久迁移机构的最小 diff
- **不奖励为复用而复用**：复用属于目标架构的行为与知识，不复用凑巧存在的结构
- **只给判断，不偷偷动手**：用户要分析时返回架构判断，不擅自把分析变成实施任务
- **警惕假第一性原理**：把测试、数据格式、运维、失败处理、用户预期里编码的行为都算进去，不为新颖而新颖
