# 复制人任务、等待与临时效果

适用于召集、治疗、训练、仪式等到场任务，闲置动作与招呼，以及殖民地临时效果、特殊死亡流程。任务页签诊断另见[任务面板与受阻原因](chores-panel-and-reasons.md)，按钮与输入另见[侧屏交互](side-screens.md)。

案例来源：Execution Platform 与 Better Action Showcase 0.2.4；目标版本 U59-744825-SCRPN。对应原生方法体已核对，编译和离线检查通过；任务寻路、修复后的渲染、启停读档、效果共存及死亡流程尚未游戏实测。项目数值与实现方案不是所有 Mod 的默认规范；换版本重新核对接口和方法体。

## 先分清数值契约

- “压力增加 20%”可能是立即增加 20 个百分点、每周期增加 20 个百分点，或将原有变化率乘以 1.2。这三种不是同一件事。确定触发时机、单位、持续时间及边界钳制，玩家文案与实际计算一致。
- “属性 +1”先明确属性集合。运动、力量、学习、挖掘等技能属性不等于数据库中的全部 Attribute；不要顺带修改最大生命、呼吸、代谢或幸福度等无关值。用明确的目标版属性 ID 集合，而非遍历所有属性。
- 明确效果对象范围：指定小人、同小行星，还是所有存活复制人；后加入者是否受影响、是否只获得剩余时长。多个世界不能依靠当前画面所在世界暗中决定范围。
- 分别约定同一效果重复触发、不同效果同时存在：刷新剩余时间不等于累加持续时间，更不等于多份 modifier 叠加。同类不叠加并不意味着不同类互斥。

## 装饰动作的资格、触发与取消

分清能否播放、选什么动作、何时安排及何时取消。闲置站稳、移动方式、携带物、换装点和原版反应等属于播放资格；压力、体力、饥饿等属于情境；冷却只限制频率，不能越过资格。条件按动作需要选择，不把某个站姿的限制套给所有角色动作。

如果动作就是为了表达某种需求，取消条件不能覆盖它的整个触发区间。例如普通疲劳选择打哈欠，极度疲劳才取消；若两者共用同一阈值，动作会刚开始就被下一次检查掐断。创建前拒绝已达取消条件的动作，排队后到实际领取时复核资格，播放中仍允许工作或求生抢占。

U59 的 `EmoteChore` 默认使用 compulsory 优先类别且不可抢占。纯装饰任务复用它的动画生命周期时，需要调整自身的 `masterPriority` 与 `IsPreemptable`；不要因任务类别叫 `EmoteIdle` 就认为默认会让位。连续闲置计时在移动或任务切换时重置，暂停和倍速沿游戏模拟时钟处理。

## 任务交接包含短暂的空状态

排队资格与接管资格要结合真实调用顺序。U59 的 `ChoreDriver.SetChore` 先 `StopChore`，再检查替代任务的 `IsValid`；旧任务结束时先清空 `currentChore`，再 `Fail` 并发送 `EndChore`。因此合法候选也会遇到“当前任务为空”的交接瞬间，旧任务的结束事件还可能重置它依赖的计时或表情。不能要求已经排队的装饰任务在这一瞬间仍看见旧 `IdleChore`。

只让自己仍持有、在有效期内且安全条件仍满足的候选跨过受控交接；新建任务仍须满足原来的闲置条件。不要把所有空任务都视为闲置，也不能让任意候选绕过资格。新的其他任务开始时仍须撤销装饰状态。需要保留动作选定的表情时，同时检查旧任务结束、延迟接管及新任务开始，不能只在 `BeginChore` 特判。

自然完成与抢占取消另查。U59 `StandardChoreBase.Succeed` 先 `End`，经 `onExit` 触发 driver 的结束事件，随后才 `Cleanup/onCleanup`；`Cancel` 也先 `End` 再 `Cleanup`，但控制器主动取消前可能已清空自有引用。不要用“完成回调总在结束事件之前”安排清理，更不能只回放取消路径就宣称自然完成已覆盖。实际控制器回放与引擎边界核对见[验证与交付](verification-and-release.md)。

## 普通人与仿生人按模型核对

先找共同创建入口，再查各模型的需求、存储、导航与动画差异，不因画面里没有动作就另挂第二份控制器。U59 的 `MinionConfig` 和 `BionicMinionConfig` 都调用 `BaseMinionConfig.BaseMinion`，并取得共同的默认闲置动画；是否真正执行到 Mod 入口仍须结合运行版本和日志判断。

U59 仿生人有共同的 Stress/Breath，没有普通人的 Stamina/Calories，另有电量、氧气罐、润滑油等需求。缺失的有机需求应按“不适用”处理，不能当成零体力或零卡路里；是否新增低电量等专属表现由功能目标决定，不把仿生需求硬塞进有机阈值。

区分搬运库存与身体内置存储。U59 原生先创建共同搬运 `Storage`，再为仿生人添加电池、增强器和氧气三个 `Storage`；内置物品不代表手里拿着货。按目标版实际搬运消费者和 `storageID` 核对用途，不能要求所有 Storage 都空；也不要把一次组件创建顺序当成其他版本或 Mod 组合的普遍保证。模型挂载、需求资格与皮肤动画渲染分别验证。

## 招呼与临时表现的所有权

改变招呼外观时保留原版配对、冷却、思绪及分段回调。U59 的招呼回调注册依赖已选好的 Emote，动作选择应在绑定前完成；指令结构不匹配时保留原方法。第三方已选自定义动作或表情时，动作和表情一起让位，不只保留身体动作却另配一张脸。

`FaceGraph` 在 U59 按 Expression 实例去重和移除。只移除自己持有的实例；同一角色的情境脸和独立招呼若会各自清理，就不要共用同一个实例。缓存需保留这个所有权边界，不能为了减少分配改变清理语义。原版强制或需求表情出现时按设计让位，不全局清空表情列表。

初始化依赖齐全后再开放模拟和事件入口；清理时先撤销就绪状态、清空自己持有的任务引用，再取消旧任务并移除自身覆盖，防止取消回调重入。周期注册与缓存范围见[性能与生命周期](performance-and-lifecycle.md)。

## 高优先级任务仍要有中断语义

指定小人的 Chore 需要目标身份前置条件，不能只提高优先级让任意工人领取。还要考虑同一个小人被两座建筑同时指定：占用的取得、释放与读档重建应一致。

PriorityClass 和数值优先级共同参与调度；某一类别的 9 不代表全游戏最高。若必要生活需求和求生可以中断等待，就保留相应调度与抢占路径，不借用强制死亡类任务实现普通召集。忽略排班与不可抢占也不是同一开关。

U59 的两个容易误读的实现：

- `StandardChoreBase.Fail(reason)` 在 `provider`、`driver` 均存在时，`runUntilComplete == false` 调用 `Cancel`，否则调用 `End`。`Cancel` 会 `RemoveFromProvider` 并清理；`End` 结束当前执行但不在这条路径移除 provider。不能仅按参数名称判断“可中断后继续存在”。其他取消路径仍需单独检查。
- `Workable.SetWorkTime(value)` 同时设置 `workTime` 和 `workTimeRemaining`。只直接写总时长可能仍按旧的剩余时长完成。无限等待需要同时初始化两者，并确认子类或原生恢复逻辑是否重写它们；读档时不要无条件覆盖保存的工作进度。

`WorkChore` 自带 `CanMoveTo` 前置条件，路径不可达不等于任务必须取消。按设计决定保留请求、显示受阻还是超时撤销，别静默把未到场操作升级为不可逆动作。是否要求建筑处于 Operational，应同时考虑到场、等待与实际执行，不照抄构造参数。

## 到场不等于已确认执行

将“选定目标 → 前往 → 等待 → 确认后执行 → 结束”分开，断电、吃饭、求生和路径变化分别决定暂停还是取消。等待中离场后按钮应反映真实状态，不能只相信早先的到场标记。

不可逆按钮的后端重新校验目标存活、有效身份、当前阶段、实际位置和运行条件；UI 禁用不是防重复执行保障。确认入口锁定执行阶段，动画回调、模拟更新和读档恢复不能各触发一次结果。

区分两种重试：尚未提交结果时恢复执行；结果已经提交时只恢复呈现或清理。死亡、扣料、立即压力变化和奖励应有恰好一次的提交边界，而不是每次 `OnSpawn` 都重放。

## 保存的是状态，不是运行时任务对象

保存稳定引用或游戏序列化身份、阶段、配置和必要进度；读档后重建 Chore、事件和动画覆盖。不要保存 UI 对象、委托或把临时组件实例当稳定身份。

在目标死亡、消失、迁移世界或建筑被拆除时释放占用并清理任务。恢复阶段与一次性后果分开：加载存档不应再次添加立即压力、发放取消奖励或执行死亡。若保存时处于动画中，明确续播、回到确认前或完成已提交结果的策略。

## 效果刷新与多来源所有权

先注册稳定的 `Effect` 资源 ID，再复用定义。U59 `Effects.Add(Effect)` 会考虑免疫与 stomp group；未被拒绝时查找已有实例，新实例才添加 modifiers，并将该实例的 `timeRemaining` 设为定义的 `duration`。这是同一效果刷新而非额外堆一份，不代表不同 ID 自动互斥。

不要每个模拟 tick 重新 `Add` 有限时效果，否则倒计时可能永远被刷新。应在规定事件发生时刷新；初始化或读档恢复也不应无意恢复完整时长。

由建筑持续维持的全局状态要汇总有效来源。两座建筑都在等待时，取消一座不能直接删除所有人的共同效果；最后一个来源结束后才移除。一次性计时余波则交给效果剩余时间，不套用持续来源的移除逻辑。持有运行时来源集合时，核对清理、游戏退出及读档重建，避免上一局残留。

特殊死亡与哀悼处理只针对独有原因或明确标记。要求某类死亡不触发 `Mourning` 时，不要禁用所有死亡、尸体搬运或坟墓行为；尸体、掉落装备和正常安葬另按设计保留。动画播放不等于真正执行了原生死亡与尸体生命周期。

## 查源码与定向验证

优先定位 `StandardChoreBase.Fail/Cancel/End`、`WorkChore` 构造及前置条件、`Workable.SetWorkTime`、`Effects.Add` 和实际死亡事件消费者。上述方法体结论来自 U59；具体任务优先级、存档恢复和死亡补丁仍须结合当前实现核对，不能用本文替代运行验证。

有相关改动时重点观察：不可达仍保留请求；必要需求中断后可回来；等待时断电/拆除；两个来源取消一个；重复触发仅刷新；效果自然到期；前往/等待/执行中存读档；目标意外死亡；原版其他死亡仍正常哀悼。按本次风险选场景，不强制每次跑全套。
