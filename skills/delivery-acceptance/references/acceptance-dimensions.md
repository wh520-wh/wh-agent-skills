# 三维度验收检查清单

> 这是 SKILL.md Step 3 的展开。每个维度都要**独立出证据**，不只读代码。

## 通用前置：建立「验收对照表」

读计划文件后，先建一张表（写在草稿/对话里即可）：

| Task | 计划要求的文件 | 关键函数/结构 | 关键测试 | 预期提交信息 | Self-Review 声明的"本期不做" |
|------|--------------|-------------|---------|------------|--------------------------|

这张表是后续「计划完成度」的判分依据，也是发现「计划要求 X 但 X 没出现」跨维度因果链的起点。

---

## 维度① 计划完成度

**问题**：计划里说的，程序员真的都做了吗？

检查动作：
1. `git log --oneline -<N>` 核实每个 Task 对应一个提交，提交信息与计划 Step "提交" 段一致。
2. `git show <hash> --stat` 核实每个提交改动的文件与计划「文件结构」表一致。
3. 逐 Task：用 Read 打开计划要求改/建的文件，确认关键函数/数据结构**真的存在且签名一致**。
4. **评审硬伤对账**：计划里若标注了 A1/A2…（来自对抗性评审的问题），逐条核实是否被对应 Task 真正修掉。例如 A1="不得重复 import" → 去测试文件 head 看是否真的只 import 一次。
5. **Self-Review 对账**：计划末尾 Self-Review 段声明"本期不做 X"，核实声明与实现一致——声明不做的确实没做，不能把"没做"伪装成"按计划延期"。

证据形式：每个 Task 一行结论 + 简短证据（commit hash / file:line / grep 结果）。

---

## 维度② 代码质量

**问题**：做出来的代码质量高不高？

读核心新文件全文 + 改动文件改动部分（`git show`），从以下维度评分（每项 1-5 分）：

1. **可读性与命名一致性**：函数命名、数据结构跨模块是否一致（如 `time{kind,elapsed,anchor,confidence}` 在产/存/读/检查四处命名是否一致）；注释是否解释 why。
2. **边界与健壮性**：null/undefined/非法输入处理；正则校验严格度；中文/跨年/超大数字解析。
3. **误报防护**（计划若强调"宁缺毋滥"则重点查）：确定性裁决是否真的只判"能稳判不误报"的硬矛盾；有没有让漏判或误判的漏洞。
4. **设计分层**：纯函数与 IO 是否分离；依赖方向是否单向无环（用 grep 核查无循环依赖）。
5. **重复/冗余**：可简化的逻辑、重复代码。

证据形式：每维度 1-5 分 + 理由 + file:line 引用。最后给总体评级（优秀/良好/合格/不合格）+ Top 3 改进建议。

---

## 维度③ Bug 审计

**问题**：项目有没有 bug？这是验收价值最高的维度——只跑既有测试永远绿，挖不出隐藏 bug。

### 第一步：跑真实测试拿基线

```bash
node --test tests/*.test.mjs tests/<子目录>/*.test.mjs   # 或项目对应命令
```

记录 pass/fail 总数。这是后续判断"修复有无回归"的基线。

### 第二步：读源码找疑点

重点找以下类型 bug（带 file:line）：
1. **逻辑 bug**：循环里状态更新逻辑、排序假设、去重指纹误判。
2. **数据流 bug**：filter 漏掉某类冲突、mergeExtraction 去重误判、迁移透传不校验。
3. **迁移 bug**：旧数据结构畸形时是否污染下游。
4. **提示词 bug**：空值时是否渲染空段、旧字段兼容性。
5. **边界**：计划测试没覆盖的"中间态"输入（如只给部分字段、纯单位数值）。

### 第三步：写探针脚本验证（核心动作）

对每个疑点写一个最小探针，用 `node --input-type=module -e '...'` 内联跑，或落临时文件跑。模板见 `../scripts/probe-template.mjs`。

**探针的目的是把"疑似 bug"变成"确认 bug"或"排除"**——不能停留在"我觉得这里有风险"。每个疑点必须有一个探针给出 yes/no。

探针套路（从真实验收提炼，可推广）：
- **边界输入**：喂计划测试没覆盖的中间态（只给部分字段、纯单位数值、裸 "0" 等）。
- **状态序列**：构造"倒退后又继续"的序列，看基准是否被污染。
- **乱序输入**：未排序的序号，看排序假设是否成立。
- **畸形透传**：构造畸形字段，看是否一路透传到渲染/检查。
- **重复输入**：构造同 key 多节点，看是否重复累加/重复比较。
- **依赖方向**：grep 核查新引入的模块间依赖是否成环。

### 第四步：分级

每个发现 bug 给：严重程度（高/中/低）+ file:line + 复现条件 + 影响 + 建议。严格区分"**确认 bug**"（有探针复现）与"**疑似需确认**"（读了代码觉得可疑但没复现）。

证据形式：bug 总数 + 分布表 + 每个 bug 的探针输出片段。

## 验收通过门槛

每个验收结果必须能落到下面三档之一。

| 维度 | 通过 | 修复后可合并 | 不可合并 |
|---|---|---|---|
| 计划完成度 | ≥95% | 90-95% | <90% |
| P0 bug | 0 | 0 | ≥1 |
| P1 bug | 0 | 1-2 | ≥3 |
| 代码质量平均分 | ≥4.0 | 3.5-4.0 | <3.5 |

**可合并判定 = 三档取最严**：

- ✅ 可合并：所有维度都在"通过"档
- ⚠️ 修复后可合并：任何维度落在"修复后可合并"档
- ❌ 不可合并：任何维度落在"不可合并"档

边界案例（计划完成度恰好 90%、P1 恰好 2 个等）按用户开局策略决定，报告必须显式说明取值依据。
