# 派修复子代理指南

> 仅当用户在开局授权“派子代理修复”，或验收中对某个问题明确授权派子代理时使用。

## 何时派

不要在三维度验收后才第一次问“要不要修”。修复策略必须在 Step 0 已经问清楚。

允许派子代理的条件：

- 用户开局选择“派子代理修复”；或
- 用户逐项确认时，对某个问题明确说“派子代理修”。

如果用户选择“先不修复”，不要派子代理；写验收报告 + fix plan。

## 派谁

general-purpose 子代理（能跑测试、写代码、做判断）。不要用只读 Explore。

## prompt 模板

```
你是资深工程师，按 TDD 执行验收中确认的修复任务。

上下文：
- 验收报告：<acceptance report path>
- 修复范围：<Fix 编号 / 文件 / 问题摘要>
- 回归命令：<test/build command>

要求：
1. 先读验收报告中对应 Fix 的问题、证据和约束。
2. 严格 TDD：先写失败测试或探针 → 跑红 → 改实现 → 跑绿。
3. 最小改动，不动无关文件，不改既有契约；若必须改契约，停下报告。
4. 全部完成后跑全量回归。
5. 如果允许 commit，用显式 `git add <具体文件>`，不要 `git add -A`。
6. 最终报告每个 Fix 的状态、测试结果、回归结果、commit hash（如有）。
```

## 诚实披露核查

子代理报告里若出现以下措辞，复审时必须核实：

- “做了等价修正” → 是否真的等价，是否弱化测试。
- “跳过某 Fix” → 理由是否成立。
- “重跑即绿” → 是否 flaky，需复跑确认。
- “已提交” → commit stat 是否只含授权文件。

## 降级路径

1. 子代理不可用：重试一次。
2. 仍失败：主 agent 接管，报告中说明独立性降低。
3. 如果用户不允许主 agent 修复：停止，写 fix plan，报告标注未闭环。

## 安全边界

- 只能改授权 Fix 相关文件和测试。
- 禁止 `git reset --hard`、`git push --force`、合并默认分支、打 tag，除非用户明确祈使句授权。
- 不得把无关未跟踪文件加入提交。
