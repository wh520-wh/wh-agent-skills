# TDD fix plan 格式

> 只在“发现问题但本轮不修复 / 用户明确要求先不修复 / 问题需要后续执行”时落盘到 `docs/superpowers/plans/<计划名>-fix-plan.md`。
> 如果问题已在验收中顺手修复并复验通过，不要写本文件；把修复记录写进验收报告。

## 文件头

```markdown
# <计划名> 修复计划

> 目标：修复验收中确认但尚未闭环的 N 个点（X 个 P1、Y 个 P2、Z 个 P3）。
> 执行方式：TDD。每条先写失败测试，跑红，改实现，跑绿，最后全量回归。
> 来源报告：`docs/superpowers/reports/<计划名>-acceptance-report.md`

## 背景

<原计划> 已交付，但验收发现以下未修复问题。本计划只包含未来要执行的工作。

---

## Fix N（P1 Bug）：<一句话标题>

**问题**：`<file>:<line>` <现象描述>。<为什么是 bug / 与哪个原则冲突>。

**修复**：<改什么，一句话>。

**Step 1 失败测试**（追加到 `<test file>`）：

\```js
test("<用例名>", () => {
  // 断言
});
\```

**Step 2 跑红**：`<test command>` → FAIL（<失败原因>）。

**Step 3 实现**：<实现方向；必要时标明 old→new>。

**Step 4 跑绿**：`<test command>`。

---

## 全量回归

\```bash
<full regression command>
\```

Expected: 全绿。

## Self-Review

- 每个 Fix 都是未修复的未来工作。
- 每个 Fix 有可执行的失败测试和跑绿命令。
- 不包含已经顺手修复的问题。
- 不包含疑似但未确认的问题；疑似风险留在验收报告。
```

## 写 fix plan 的纪律

- 只写未来要执行的工作。
- 不要为已经修好的问题补写事后计划。
- 每个 Fix 的测试必须可执行；不能写“补测试即可”这种空话。
- 宁缺毋滥：不确定是不是真 bug 的，不要塞进 fix plan。
